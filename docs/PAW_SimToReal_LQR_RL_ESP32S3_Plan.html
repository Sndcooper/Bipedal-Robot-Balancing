PAW wheel-legged biped · plan v1 · Nov 2026

From the real robot to a matching simulator, then LQR and RL on an ESP32-S3

One measured model of the real robot feeds both controllers. LQR gets you a provably stable balancer fast. The same model, with randomised parameters, trains an RL policy. Both run on the ESP32-S3, which replaces the STM32F103.

00

Read this first

The simulator is the centre of everything. If the sim matches the real robot, LQR gains copy straight across and RL policies transfer. If it doesn't, both fail on hardware. So most of the effort goes into measuring the robot and checking the sim against logged real data, before any controller work.

Reading order

  1. Architecture: how the three tracks connect and what runs where.
  2. Phases & gates: the order of work, and the test each phase must pass before you move on.
  3. Measure the robot: the parameter table. Start measuring this week; it blocks everything else.
  4. ESP32-S3 port: can start in parallel with modelling. Order the board and level shifters now.
  5. Sim model → LQR → RL: in that order.
Three decisions this plan makes for you

Simulator: MuJoCo (with MJX / MuJoCo Playground for GPU RL). Your legs are a closed 5-bar loop; MuJoCo handles loop closure natively with equality constraints. Isaac Lab / PhysX articulations are trees and need workarounds for closed chains.

Controller input: motor voltage (PWM duty), not torque. You have no current sensing, so model the motor electrically and let LQR and RL command what the firmware actually sets.

RL deploys as residual-over-LQR first. The policy adds a correction to the LQR command, clipped. LQR stays as the safety net while you learn how the policy behaves on hardware.

LQR

Linearise the validated model around upright at several leg heights. Solve the discrete Riccati equation for each. Interpolate gains on the MCU by current leg height. Expected outcome: stable balance with no hand-tuned PID cascade.

RL

Same MJCF, wrapped in a Gym/Playground environment with randomised mass, motor and latency. PPO trains a small MLP (about 20k parameters). Expected outcome: balance plus velocity, yaw and height tracking, and push recovery beyond what a linear controller handles.

Change the motor driver before you model it

Your own research notes (docs/PAW_Research_Notes.md, finding 7) already flag the L298N. Its 2 V voltage drop varies with current and its ~1 kHz PWM causes audible, nonlinear behaviour near zero. A TB6612FNG (or DRV8871 per motor) at 20 kHz is close to linear, which makes the motor model, the LQR and the RL policy all transfer better. Swap it during the ESP32-S3 rewire so you only identify the motors once.

04

Build the simulation model

modelshared with RL

Pipeline

  1. CAD to URDF. Open bipedal_assembly.f3d in Fusion and export with the fusion2urdf add-in, or build the URDF by hand from the per-part STLs in parts_stl_assembly_pose/. Each joint origin must sit exactly on a servo horn or wheel axis.
  2. URDF to MJCF. Load in MuJoCo, save as XML, then edit by hand. From here on sim/model/paw.xml is the source of truth, generated from paw_params.yaml by a small Python script so values never drift.
  3. Close the leg loops. URDF can't express the 5-bar. Model each leg as two open chains (left femur → left tibia, right femur → right tibia) and join the two tibia ends with an equality connect constraint. The wheel axle hangs off one tibia.
  4. Replace CAD inertias with measured ones. Use inertial tags with the measured mass and CoM; scale inertia from CAD shape to the measured mass.
  5. Add actuators that behave like the real hardware (below), and sensors matching the real ones: gyro, accelerometer, wheel joint position (quantised to encoder counts), servo position.
  6. Keyframes for standing at 5 leg heights (e.g. foot y = 100, 115, 130, 140, 150 mm), solved with your existing IK so sim and firmware agree on servo angles.

What makes the sim "the real robot"

Mass and geometry are the easy part. Sim-to-real gaps on robots this size almost always come from the actuators and timing. Model all of these explicitly:

Wheel motor

  • Voltage input with back-EMF (above)
  • Rotor inertia reflected as armature = J·N²
  • Coulomb + viscous friction
  • Driver deadband and voltage drop, battery sag (10.5–12.6 V)
  • Backlash: a small free-play joint or a deadzone on the encoder reading

AX-12 servo

  • P-controller with torque limit 1.5 N·m and speed cap ~6 rad/s
  • Compliance margin/slope mapped to kp
  • Position quantised to 1024 steps over 300°
  • Command delay: 100 Hz update + bus transaction time

Sensors

  • Gyro and accel noise and bias from the stationary log
  • Encoder quantisation to real CPR
  • IMU mounted at its real position on the body (accel sees centripetal terms)

Timing

  • Sim timestep 1 ms, controller runs every 2.5 ms (400 Hz)
  • One-step action delay buffer equal to measured latency
  • Same filters (complementary / Kalman) as firmware, ported 1:1

05

LQR design

LQR

State and input

Treat the robot as a wheeled inverted pendulum whose pendulum length changes with leg height. Legs are held by the servos, so for balance they are a slow, separate subsystem.

x = [ p, ṗ, θ, θ̇, ψ, ψ̇ ]ᵀ p = forward position (from wheel encoders) θ = body pitch, ψ = yaw u = [ V_L, V_R ]ᵀ motor voltages (PWM duty × V_batt) Nonlinear model (sagittal plane, m_b body, m_w wheels, l = CoM height above axle): (m_b + m_w + I_w/r²)·p̈ + m_b·l·cosθ·θ̈ − m_b·l·sinθ·θ̇² = τ/r m_b·l·cosθ·p̈ + (I_b + m_b·l²)·θ̈ − m_b·g·l·sinθ = −τ τ = τ_L + τ_R from the motor model; yaw uses (τ_R − τ_L)·(d/2r) Linearise at θ = 0 → ẋ = A(l)·x + B(l)·u → discretise at Ts = 2.5 ms → Φ, Γ Discrete LQR: K = (R + ΓᵀPΓ)⁻¹ ΓᵀPΦ, with P from the DARE Control law: u = −K(l)·(x − x_ref) + u_ff

Two ways to get A and B (do both and compare)

Analytic, 6-state

From the equations above with measured parameters. Easy to read, easy to schedule over l. Use it to sanity-check the numerical one.

Numerical from MuJoCo

mjd_transitionFD on the full MJCF at each standing keyframe, then reduce to the 6 balance states. Captures leg masses and the IMU offset the analytic model ignores.

import mujoco, numpy as np, scipy.linalg as sla

m = mujoco.MjModel.from_xml_path("sim/model/paw.xml"); d = mujoco.MjData(m)
gains = {}
for k, height in enumerate([100, 115, 130, 140, 150]):        # mm, one keyframe each
    mujoco.mj_resetDataKeyframe(m, d, k); mujoco.mj_forward(m, d)
    nx = 2 * m.nv + m.na
    A = np.zeros((nx, nx)); B = np.zeros((nx, m.nu))
    mujoco.mjd_transitionFD(m, d, 1e-6, True, A, B, None, None)  # discrete, at m.opt.timestep
    Ar, Br = reduce_to_balance_states(A, B, m)                   # pick p, θ, ψ and rates; wheel inputs only
    Ar, Br = resample(Ar, Br, Ts=0.0025)                         # match firmware loop rate
    Q = np.diag([20, 2, 400, 10, 5, 1]); R = np.diag([1, 1]) * 0.5
    P = sla.solve_discrete_are(Ar, Br, Q, R)
    gains[height] = np.linalg.solve(R + Br.T @ P @ Br, Br.T @ P @ Ar)
write_c_header("firmware/include/lqr_gains.h", gains)          # float K[5][2][6]

Tuning Q and R

  • Start with Bryson's rule: Qii = 1 / (max acceptable error)², Rii = 1 / (max voltage)². For example, θ max 3° → Qθθ ≈ 365; p max 0.2 m → 25; V max 8 V → R ≈ 0.016.
  • Raise R if wheels chatter or saturate; raise Qθθ if it leans too far before reacting.
  • Check closed-loop poles: all inside the unit circle with a margin, and the fastest pole well below the Nyquist of the loop rate.
  • Run a Monte-Carlo of 200 sims with ±20% parameter error and added latency. Pick the Q/R that survives all of them, not the one that looks best on the nominal model.

Practical additions on top of plain LQR

  • Gain scheduling: linearly interpolate K between the two nearest leg heights every loop.
  • Integral action on pitch offset (LQI) or a slow CoM-offset estimator, to remove lean bias from battery or IMU mounting. This replaces the PID integrator that your logs show saturating.
  • Velocity command: drive by moving x_ref (p_ref integrates the commanded speed, ṗ_ref = command). No separate outer PID needed.
  • Friction / deadband feed-forward in u_ff, using the measured deadband.
  • State estimate: θ from a complementary or small Kalman filter at 400 Hz; ṗ from encoder differences, low-passed at ~30 Hz, not the 2.6 Hz EMA the current firmware uses.

ESP32-S3 port

MCU

The ESP32-S3 has two 240 MHz cores and a single-precision FPU, so LQR, a Kalman filter and a 20k-parameter MLP all fit inside a 400 Hz loop with room to spare. It also has hardware quadrature counters (PCNT) and a motor PWM peripheral (MCPWM), which fix two weaknesses of the current STM32 setup.

07

RL environment

RL

The RL environment is the validated MJCF plus randomisation, a reward and a curriculum. Only start this after P2, because a policy trained on an unvalidated model learns to exploit the model's mistakes.

Tooling

Recommended: MuJoCo Playground (MJX, JAX)

Thousands of parallel environments on one GPU; trains balance in minutes. Ships PPO via Brax. Works on a free Colab GPU if you have no local GPU.

Fallback: Gymnasium + Stable-Baselines3

CPU MuJoCo, 16–32 parallel envs. Slower (hours) but simpler to debug. Use it to prototype the reward, then move to MJX.

Curriculum

  1. Balance in place, fixed leg height, small randomisation.
  2. Full randomisation, random leg heights, pushes.
  3. Velocity and yaw-rate commands.
  4. Height changes while moving; small floor bumps and slopes.
  5. Optional later: jumps using leg extension, as Ascento and Diablo do.

Residual RL first

In the residual variant the policy observes the same inputs plus the LQR output, and its action is added to it: u = u_LQR + clip(α·a, ±2 V). Training is fast because LQR already balances, and on hardware a bad policy can only nudge a working controller. After that works, train the full policy with the same interface and compare.

# PPO settings that are a reasonable starting point for this size of task
policy: MLP [128, 128], ELU;  critic: MLP [256, 256] with privileged obs
num_envs: 4096 (MJX) | 32 (SB3);  episode: 20 s;  control dt: 5 ms

08

Deploy & safety

MCURLLQR

Getting the policy onto the ESP32-S3

  • Export weights, biases and observation mean/std to policy_weights.h as float arrays. A [24→128→128→4] MLP is about 20k multiply-adds: roughly 0.1–0.3 ms on one S3 core in plain C with -O2.
  • Write the forward pass yourself (three loops and an ELU). If you need more speed, use ESP-DSP's dot-product or ESP-DL with int8 quantisation; you likely won't need it.
  • Verify bit-exactness: feed 1000 recorded observations to the C code on the host and on the S3, compare against PyTorch/JAX output. Max error should be < 1e-4.

Hardware test protocol

  1. Wheels off the ground on a stand: verify signs. A forward lean must spin wheels forward.
  2. Harness (string from above, slack): LQR at the middle leg height.
  3. Free balance, then all five leg heights, then push tests with a consistent tap.
  4. Record every run; overlay with sim using the same push in the plotting script.
  5. Repeat 2–4 with residual RL, then full RL.

What to study

Robots like yours

  • Upkie: open-source wheeled biped with MuJoCo/Bullet sims, LQR-like and PPO balancers. Closest reference project.
  • Ascento (ETH Zürich) papers: LQR on a wheel-legged robot with a variable-height leg; gain scheduling over height.
  • Direct Drive Diablo and Unitree wheel-legged work: RL locomotion on the same morphology.

Simulator and RL

  • MuJoCo modelling guide: equality constraints, actuators, mjd_transitionFD.
  • MuJoCo Playground: GPU RL environments and sim-to-real examples.
  • Stable-Baselines3 PPO docs.

Control theory

  • Wheeled inverted pendulum derivation: Grasser et al., "JOE: a mobile, inverted pendulum" (2002).
  • Bryson's rule for Q/R; LQI for integral action.
  • python-control and scipy.linalg.solve_discrete_are.

ESP32-S3

  • PCNT (quadrature encoders)
  • MCPWM (motor PWM)
  • GPIO and strapping pins
